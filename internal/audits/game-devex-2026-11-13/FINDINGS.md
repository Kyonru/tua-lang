## GAME-01: imported protocol bound changes class subtype assignability

- **Category / severity:** correctness; High. **Verification:** independently reproduced in the CLI with a four-variant matrix and emitted-Lua runtime check. The first trial was the procedural stealth-maze game.
- **Minimal project:** [`trials/maze/repros/inheritance_alias/`](trials/maze/repros/inheritance_alias/). `src/actors.tua` exports `ActorInstance`, `GuardInstance`, and `Alertable`; `Guard extends Actor implements Alertable`. `src/main.tua` imports them, defines `alarm<T: Alertable>`, then assigns a `GuardInstance` parameter to a fresh `ActorInstance[]`. The same file also assigns `Guard.new(...)` directly to that array type.
- **Reproduce:** from the minimal project, run `/Users/kyonru/Documents/projects/Experiments/tlua/target/debug/tua check`. It exits 1 with `src/main.tua:10:37 error TL1003: type mismatch: expected ActorInstance, found GuardInstance`. The unused `alarm` warning is independent of the error.
- **Expected:** both values are instances of the same `Guard` subclass. The documented [base-typed array example](../../../docs/classes.md) accepts direct subclass constructors. Adding a separate generic function should not change assignability in another function.
- **Controls:** on a copy of the project under `/private/tmp/tua-game-devex-alias-recheck/`, deleting `alarm<T: Alertable>` makes `tua check` pass; changing it to unbounded `alarm<T>` also passes; leaving the unused protocol import without the bound passes. Direct construction passes in the failing file. `tua build --emit-on-error` writes Lua despite the diagnostic, and `lua main.lua` from its `build/` directory exits 0 after both array assertions. The runtime check used Lua 5.4, not LuaJIT/LOVE.
- **Independent second form:** the arena game reduced this to [`trials/arena/repros/imported-base/`](trials/arena/repros/imported-base/). `core.tua` assigns a `DefenderInstance` local to `ActorInstance` and later declares `Tickable[] = { Defender.new() }`. `tua check` reports `src/game/core.tua:6:29 error TL1003: type mismatch at base: expected ActorInstance, found DefenderInstance`. A direct constructor assignment to `ActorInstance` in the same file passes. Removing only the later protocol-typed array makes the earlier assignment pass; the lead reproduced both results on a copy. This corroborates a shared protocol/imported-alias interaction rather than a game-specific mistake.
- **Likely boundary, not yet proven cause:** imported alias/class identity and the generic protocol bound are combined in the checker type context. The context records nominal alias parentage and generic bounds in [`types/environment.rs`](../../../crates/tua-core/src/types/environment.rs) around `to_type_context` and compares nominal aliases in [`types/assignability.rs`](../../../crates/tua-core/src/types/assignability.rs) around `check_assignable_inner`. The experiment establishes an interaction, but does not isolate the faulty insertion or lookup.
- **Coverage gap:** the bundled [`polymorphism.tua`](../../../examples/features/src/polymorphism.tua) tests direct constructors in a base-typed array; it does not pass a subclass through an imported instance alias while a bound generic function is in scope.
- **Fix direction and regression:** retain canonical imported class identity when registering a generic protocol bound. Add one project-level positive check for the alias parameter with and without the bound, one negative check for an unrelated class, and an LSP diagnostic/edit-recovery test. Recheck hover/completion on the same expression before declaring editor parity.

## GAME-02: project-root shader paths fail after source-root build relocation

- **Category / severity:** correctness and documentation; High. **Verification:** independent check/build/LÖVE replay with failing and passing paths. The first trial was the alchemy game.
- **Minimal paired reproduction:** [`trials/alchemy/repros/shader_source_path/`](trials/alchemy/repros/shader_source_path/) and [`shader_build_path/`](trials/alchemy/repros/shader_build_path/) differ by the literal path. From **each** fixture directory, run `tua check` and `tua build` first; both exit 0. Then, from `trials/alchemy`, run `python3 run_love_smoke.py repros/shader_source_path`: it prints `source-path load false ... cannot read shader include "src/assets/pulse.glsl"`. The smoke exits 0 because the fixture catches the shader error. The full alchemy game with the same failing path also passed `tua check` and `tua build`, then printed that error in LÖVE.
- **Control:** `python3 run_love_smoke.py repros/shader_build_path` prints `build-path load true nil`. The source file is `src/assets/pulse.glsl`; build copies it to `build/assets/pulse.glsl`. The lead independently ran both `check` and LÖVE commands against the paired fixtures.
- **Expected:** a path that `check`/`build` accepts and the [bundled shader example](../../../examples/features/src/shaders.tua) explicitly describes as project-root-relative should load in the built game. Alternatively, Tua should diagnose that the source-root prefix cannot exist at runtime and document build-relative paths.
- **Likely root cause:** [`vendor/runtime/tuashaderscan.lua`](../../../vendor/runtime/tuashaderscan.lua) passes the literal path to `love.filesystem.read`, while CLI output mirrors paths relative to the configured source tree. The CLI and editor shader index can resolve the source path, but the runtime has no corresponding source-root mapping. Existing runtime tests use a `shaders/` path whose source and built locations happen to match, so they miss this layout.
- **Fix direction and regression:** define one asset-path contract across analysis, emitted Lua, and the runtime, with source-root relocation covered. The smallest safe route may be build-relative path syntax plus a precise diagnostic for `src/`-prefixed paths, and a corrected example; supporting both syntaxes would need unambiguous runtime mapping. Add an end-to-end `src/assets/` shader build and LOVE smoke, including an include and reload.

## GAME-03: imported class constructor and factory values lose receiver identity

- **Category / severity:** correctness; High. **Verification:** independent CLI matrix and emitted-Lua runtime check. The first trial was the stealth maze.
- **Minimal project:** [`trials/maze/repros/factory_forward/`](trials/maze/repros/factory_forward/). `actors.tua` exports a `Guard` class and `GuardInstance` alias; `rules.tua` imports the alias and returns `Guard.new()` as `GuardInstance`; `main.tua` calls `guard:level()` on the returned value.
- **Reproduce:** run `tua check` from that project. It exits 1 at `src/main.tua:3:15` with `TL1003: type mismatch at self: expected Guard, found Guard`. This message also hides the identity/provenance issue from the developer.
- **Controls:** adding `import type { GuardInstance } from "./actors"` to `main.tua` and annotating `local guard: GuardInstance = Rules.make()` makes the check pass. Replacing `Rules.make()` with a direct imported `Actors.Guard.new()` still fails at `guard:level()`, so the problem is broader than forwarding. `tua build --emit-on-error` writes Lua, and `lua main.lua` from the build directory exits 0 after asserting the method result.
- **Expected:** [class documentation](../../../docs/classes.md) says imported instances keep method types and colon-call behavior. Both identical-looking `Guard` types should refer to the same declaration; an unannotated constructor result should not need a redundant type annotation.
- **Editor disagreement:** running [`lsp_probe.py`](trials/maze/repros/factory_forward/lsp_probe.py) against the current `tua lsp` returns `level` in completion, hover `(method) level: () -> number`, and definition at `actors.tua:2` for the same expression that `tua check` rejects. The lead independently reran the probe. This is protocol-level evidence, not visible VS Code menu timing.
- **Likely boundary, not proven cause:** imported constructor, instance alias, and method receiver identities are being compared through different project type provenance paths. Type context construction is in [`types/environment.rs`](../../../crates/tua-core/src/types/environment.rs); alias/nominal comparisons are in [`types/assignability.rs`](../../../crates/tua-core/src/types/assignability.rs). The editor finds the right method declaration, so this appears to be a checker assignability problem rather than missing member lookup.
- **Coverage gap and fix direction:** extend the project tests beyond annotated imported instances to an inferred imported constructor result, one-hop typed factory, and a negative wrong-class receiver. Preserve canonical declaration identity through module exports and inferred returns; test CLI diagnostics, hover, completion, and recovery after an unsaved provider edit.

## GAME-04 and GAME-05: imported signal payloads disagree across checker and signature help

- **Category / severity:** GAME-04 correctness, High; GAME-05 editor usability, Medium. **Verification:** independently reproduced using CLI controls and real stdio LSP.
- **Minimal project:** [`trials/arena/repros/event-signature/`](trials/arena/repros/event-signature/). `events.tua` creates a bus and registers `on("hit", function(damage: number) ...)`, then exports it. `main.tua` imports the bus into local `bus`; `direct.tua` calls through `EventModule.events`.
- **Checker matrix:** `tua check` passes the original positive calls. On separate copies, replace the payload with `"bad"` in `main.tua` or `direct.tua`: both still exit 0. Add `events:emit("hit", "bad")` in the declaring file: check exits 1 with `TL1003: type mismatch at damage: expected number, found string`. The lead reproduced all four variants in `/private/tmp/tua-event-recheck/`.
- **Editor matrix:** run [`probe.py`](trials/arena/repros/event-signature/probe.py). Imported local `bus:emit("hit", …)` signature is typed (`value1: number`), and same-file `events:emit` is typed (`damage: number`), but direct `EventModule.events:emit` shows generic `name: string, ...: any`. The lead reran the probe. These are protocol responses, not visible menu paint.
- **Expected:** a static bus export should preserve its declared event schema across both access forms, and the checker should reject a wrong payload. Typed signature help should use the same schema. The 0.8.0 changelog claims imported SignalBus fields retain payload types; this fixture shows a narrower case that still fails.
- **Likely boundary, not proven cause:** shared signal identity/provenance at the module boundary. The checker calls event-schema resolution in [`check/mod.rs`](../../../crates/tua-core/src/check/mod.rs) near `check_signal_emit_payload_call`, while signature help uses [`signature_help/mod.rs`](../../../crates/tua-core/src/signature_help/mod.rs) near `signal_emit_payload_function`. The different outcomes for a local alias and direct field show the two surfaces are not consuming one stable event identity here.
- **Coverage gap and fix direction:** add a project-level event fixture with same-file, imported local, and direct module-property calls, each positive and negative, then replay an unsaved edit to the listener parameter type. Carry a canonical event schema through module exports and receiver aliases; have both checker and signature help resolve it from that fact.

## GAME-06: incomplete colon edit loses imported generic members

- **Category / severity:** editor editing/recovery, Medium. **Verification:** independent paired stdio LSP requests on the alchemy project; no installed-editor paint timing claim.
- **Reproduce:** from [`trials/alchemy/`](trials/alchemy/), run `node lsp_probe.js --incomplete`. The unsaved overlay ends its guarded recipe branch with `local jar = Recipes.seal(potion)` and `jar:`; completion at line 6, character 6 returns `[]` cold and warm, hover on `jar` is null, and the parser publishes two TL0001 recovery diagnostics. Run `node lsp_probe.js` with `jar:label()` at the same position: completion returns `label, get`, hover shows `Jar<Potion>`, and diagnostics are empty. The lead reran both modes.
- **Control:** [`lsp_simple_probe.js`](trials/alchemy/lsp_simple_probe.js) returns the `label` member for a same-file non-generic `object:` despite its incomplete syntax. The gap is therefore not universal colon recovery. A separate unsaved edit/revert probe preserves completed-call imported generic members, narrowing the problem to incomplete source recovery.
- **Expected:** completion should help write a member at the moment the colon is typed, using the last recoverable receiver expression. The completed-call result establishes that the type information exists.
- **Likely boundary and test:** parser recovery or semantic receiver lookup for an incomplete local initialized by an imported generic result inside a narrowed branch. Add a minimal same-file/imported generic × complete/incomplete matrix and an LSP edit sequence; preserve the previous good receiver type where the incomplete token is at the cursor without hiding real diagnostics.

## GAME-07: formatter invents indentation after exported generic alias

- **Category / severity:** formatter readability, Medium. **Verification:** independent one-file CLI replay.
- **Minimal project:** [`trials/alchemy/repros/format_generic/`](trials/alchemy/repros/format_generic/). Starting from `final class Box<T> { ... }`, `export type BoxInstance<T> = Box<T>`, and top-level `return { Box = Box }`, `tua check` passes. Run `tua fmt`: the top-level return becomes `  return { Box = Box }`. `tua check` and `tua fmt --check` then pass that output.
- **Expected:** formatting preserves syntactic top-level indentation. The formatter's spacing around generic class delimiters is a current tested style (`formatter/tests.rs` explicitly expects `Base < T >`), so that spacing is not counted as this defect.
- **Likely boundary and test:** the exported generic alias leaves the formatter's indentation state one level too deep. Add a single regression combining a generic class, exported generic instance alias, and following top-level statement, asserting idempotence and exact indentation. The emitted Lua/runtime behavior is unaffected in this fixture.

## GAME-08: constructor lowering discards assignments after inline `super()`

- **Category / severity:** emitted-Lua correctness; High. **Verification:** independently reproduced by the lead with a checked, built project and Lua runtime result. First found in the arena-defense game, where this changed player movement.
- **Minimal project:** [`trials/arena/repros/init-order/`](trials/arena/repros/init-order/). `FastInline` and `FastMultiline` both extend `Base`, whose `speed` field defaults to `0`. Their `init` bodies each call `super()` and assign `self.speed = 120`; the only difference is whether the statements share a line.
- **Reproduce:** from that project, run `tua check` and `tua build`, then from `build/` run `lua -e 'local result=dofile("main.lua"); print("inline",result.inline,"multiline",result.multiline)'`. Check and build pass, but Lua prints `inline 0 multiline 120`. In generated `build/main.lua`, `FastInline_new` returns a flattened table containing `speed = 0` without calling `FastInline_init`; `FastMultiline_new` takes the init path and yields `120`.
- **Expected:** whitespace and line placement do not change constructor semantics. The [class documentation](../../../docs/classes.md) describes initialization and field-default ordering without a one-statement-per-line restriction.
- **Likely root cause:** [`self_assignments`](../../../crates/tua-core/src/classes.rs) around line 2589 treats any line beginning with `super(` as the entire leading super call and skips that line. It therefore misses a following semicolon-separated assignment. [`flatten_class_constructor_with_substitutions`](../../../crates/tua-core/src/classes.rs) around line 2558 then sees no assignment, includes only the default `speed = 0`, and enables the fast constructor path. With a line break, both writes are seen and the duplicate-key guard chooses the ordered init path. This source explanation is inferred from the code and paired output; the runtime divergence is directly observed.
- **Coverage gap and fix direction:** existing [`emit/tests.rs`](../../../crates/tua-core/src/emit/tests.rs) tests default/assignment ordering, but not two statements on the same line. Parse constructor statements rather than whole lines for flattening, or conservatively disable flattening when a line contains more than one statement. Add paired inline/multiline tests asserting emitted Lua runtime parity, including parent arguments and duplicate field writes.

## GAME-09: audio snapshot hides its nested music shape

- **Category / severity:** type capability gap; Low. **Verification:** the alchemy trial checked the mistaken `audio:snapshot().musicState == "lab"` assertion without a diagnostic, then LÖVE failed the assertion. Changing it to `audio:snapshot().music.state == "lab"` passes its LÖVE smoke. This was a trial-code mistake that typing could have caught; audio runtime itself behaved as implemented.
- **Cause and contract:** [`snapshot_type`](../../../crates/tua-core/src/audio.rs) around line 448 describes the outer record but declares `music`, `buses`, and `analysis` as `Type::Any`. [`tuaaudio.lua`](../../../vendor/runtime/tuaaudio.lua) around line 601 returns a nested `music` table with `state` and `pending`. The [audio docs](../../../docs/audio.md) say the subscription state has `musicState`, while `snapshot()` has music state, but do not show the exact nested shape; the two APIs were easy to confuse.
- **Fix direction and regression:** type the stable nested snapshot fields from the runtime contract and document a short access example. Check a valid `snapshot().music.state`, reject invalid top-level `snapshot().musicState`, and verify hover/completion. If runtime shape is intentionally open, preserve known fields alongside an open extension rather than making the whole subtree `any`.

## GAME-10: pool warning is noisy after ECS ownership transfer

- **Category / severity:** diagnostic usability gap; Low. **Verification:** the alchemy game at [`src/main.tua`](trials/alchemy/src/main.tua) acquires a pooled particle, attaches it as an ECS component, and releases it from a system callback through `spark`. `tua check` emits TL5007 because it sees no later `release(particle)`; the LÖVE smoke checks pool `activeCount()` moves from 12 to 0 after updates. The warning explicitly says it cannot see a later same-file release, so it is conservative rather than a false factual leak claim.
- **Likely cause and direction:** [`object_pool.rs`](../../../crates/tua-core/src/object_pool.rs) around line 463 uses lexical release detection and does not follow an ECS ownership transfer. Consider an explicit ownership-transfer or warning-suppression form, or narrow the warning to values provably retained by the same scope. A regression should preserve warnings for genuinely forgotten releases while allowing an annotated ECS handoff.

## GAME-11: bound on exported generic instance alias needs a language decision

- **Category:** design/documentation question, not a confirmed defect. The alchemy trial used `final class Jar<T: Named>` and tried `export type JarInstance<T: Named> = Jar<T>`; the parser rejected the bound on the alias. It then used an unbounded instance alias and constrained the exported `seal<T: Named>` function, which checked and ran. The current plan and docs need a clear canonical spelling for exported bounded class instance types. If alias bounds are outside the grammar, document the working pattern; if intended, add grammar/checker/editor/runtime tests before claiming support.

## GAME-12: nested imported generic field has completion but no hover

- **Category / severity:** editor consistency; Medium. **Verification:** real stdio LSP request sequence in [`trials/arena/lsp_probe.py`](trials/arena/lsp_probe.py), independently rerun by the lead. The probe adds an unsaved `local trialActor = Game.selected.value`, where `Game.selected` is `Slot<DefenderInstance>` imported from another file.
- **Actual:** hover on `Game.selected` shows `Slot<DefenderInstance>`, but hover at two offsets on `.value` returns null. Hover on `trialActor` reports `Defender`; completion after `Game.selected.value.` offers `update`, `speed`, `progress`, and `elapsed`. The root replay observed the same results. These are server responses, not rendered editor behavior.
- **Expected and direction:** the field token should show its specialized value type, matching the receiver used for completion and the inferred local. Share instantiated generic field lookup between hover and completion. A regression should request both at the same nested chain after an unsaved edit and check source range plus type, not merely non-null hover.

## GAME-13: formatter second-pass symptom needs a preserved input

- **Category:** unverified candidate, excluded from confirmed counts. The maze trial saw `fmt` succeed and immediate `fmt --check` request another format while a multiline conditional was present. Simplifying the conditional allowed three repeated cycles to pass, but no minimal pre-format input was retained. The current game passes `fmt --check`. Reproduce on a preserved source copy and compare first/second outputs before attributing this to the formatter; no root cause is established.
