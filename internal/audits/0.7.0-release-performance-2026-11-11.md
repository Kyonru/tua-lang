# Tua 0.7.0 release-candidate performance check

Date: 2026-11-11. Revision: `ac4b771d4e9236de82d3f7148d0ea7718523f940`.
Release binary SHA-256: `0ebdef9b24cb08f4323eaeef9ef630fb7b013add480135f12938a2f9ecb927c5`.
Host: macOS 26.6.1, arm64; Node 24.15.0; Lua 5.4.8. Measurements are
protocol round trips or process timings, not VS Code key-to-menu latency.
No product source was changed for this check.

## Assessment

The CI-sized representative fixtures and bundled projects remain responsive.
An independent, local LOVE project returned correct cross-file suggestions:
three fresh-server cold requests took 441–457 ms; the first completion after an
unsaved edit took 269 ms, and subsequent edit completions took 83–90 ms. Warm
completion took less than 1 ms. These cold and first-edit delays are noticeable
for the user who is waiting for suggestions.

The 1,000-module synthetic workspace remains outside the qualified performance
envelope. Cold completion and hover are about 2.8 seconds. One contended edit
peaked at 1.40 GiB RSS, matching the previous 1.39 GiB measurement. Three
contended edits peaked at 2.52 GiB and made post-edit completion reach 1.85
seconds p95. The higher memory result is workload-dependent; it is not evidence
of a regression from the earlier, lighter measurement or proof of a leak. The
three background requests were canceled as designed. Two valid-document
completions arrived and no stale result was recorded.

Performance qualification for general release remains incomplete. The current
evidence supports beta use and ordinary-sized projects on this host, but does
not establish long-session memory stability, key-to-menu latency, or acceptable
behavior for very large projects.

The first formatting request on the local project took about 278 ms, but the
immediately repeated request took 0.37 ms and formatting the other open file
took about 1.3 ms. The first measurement includes workspace initialization and
must not be attributed to the formatter alone. Format-on-save UI latency was
not measured.

## Reproduction

The public benchmark commands, run with `target/release/tua`, were:

```sh
TUA_REPRESENTATIVE_FIXTURES=project-1000 \
TUA_REPRESENTATIVE_COLD_REPEAT=3 \
TUA_REPRESENTATIVE_WARM_REPEAT=1 \
TUA_REPRESENTATIVE_CONTENTION_REPEAT=1 \
TUA_REPRESENTATIVE_BACKGROUND_BURST=1 \
node editors/vscode/scripts/lsp-representative-profile.js target/release/tua

TUA_REPRESENTATIVE_FIXTURES=project-1000 \
TUA_REPRESENTATIVE_COLD_REPEAT=3 \
TUA_REPRESENTATIVE_WARM_REPEAT=5 \
TUA_REPRESENTATIVE_CONTENTION_REPEAT=3 \
TUA_REPRESENTATIVE_BACKGROUND_BURST=1 \
node editors/vscode/scripts/lsp-representative-profile.js target/release/tua

TUA_SPEED_WARMUP=1 TUA_SPEED_REPEAT=3 \
node scripts/profile-examples.js target/release/tua
```

The first 1,000-module command exits nonzero because its single contended
completion happened on an invalid-document probe, leaving no valid-document
contention sample. The second exits nonzero because 2.52 GiB exceeds the
benchmark's 2 GiB memory budget. Both wrote complete measurements. Neither
exit is a compiler or server crash. A first attempt failed when the sandbox
denied `ps` used by the memory sampler; a later comparable attempt was
interrupted by a tool-server restart. Successful runs above used process
inspection permission.

The local LOVE project and its source are not part of this report. Its LSP
replay opened two project files, used an unsaved cross-file store-member
expression, requested completion/hover/formatting, edited the importer and
dependency, and checked the returned labels. The soak repeated the same
unsaved completion and hover probes. Raw local data were written only to
`/private/tmp/tua-070-*` on this host.

## Follow-up before a broad release claim

1. Profile retained memory across repeated contended edits in the 1,000-module
   fixture. Separate live semantic state from allocator retention and identify
   which request or invalidation stage raises the peak.
2. Reduce cold and first-edit completion latency without losing cross-file
   types. Recheck the local project and both 100- and 1,000-module fixtures.
3. Run a longer installed-editor soak, actual VS Code key-to-menu timing, and
   LOVE/LuaJIT runtime measurements. The 30-edit protocol soak cannot qualify
   these workflows.
