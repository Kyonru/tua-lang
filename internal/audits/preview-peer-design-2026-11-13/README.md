# Tua preview design review against established game tools

Date: 2026-11-13. Starting revision: `73876da1`. This review compares **tasks and information architecture**, not the artwork or code of another product. The comparison is an inference from the linked official product documentation. Existing Tua behavior was checked in extension source, the November 11 preview audit, and the VS Code webview host suite. The host suite exercises controlled fixtures; it does not establish behavior in a long-running game.

## Summary

This review inventories 16 current preview or information surfaces and six plausible new ones. Six existing views had a clear, source-backed task improvement and were changed: sprite timing, state-machine routes, ECS relationships, server health interpretation, font sample text, and procedural regeneration status. The other views already have a useful domain shape or lack the data needed for an honest new UI. The highest-value next step is compiler-backed navigation across views, followed by large-project and live-session qualification. Stores currently has no dedicated static preview; its live history remains in the Runtime Inspector.

## Design principle

A preview earns a panel when it answers a question faster than reading source. A static compiler snapshot must say what was *declared*. A running-game sample must name the session and sample age. An isolated demo must say that it does not run the user's game. This boundary matters more than visual similarity to Aseprite, Godot, Unity, or FMOD.

The primary design goal is **exploring relationships across a game**. A developer should be able to follow a component to systems that access it, an event to its emitters and listeners, or a module to the import that brought it into a build, then open the exact source declaration. A relationship button and a source button serve different tasks. Cross-view links should be added only when compiler-owned IDs and ranges identify both ends; matching display names is insufficient.

## Existing surfaces and recommended direction

Status: **rendered** means the production template ran in the VS Code webview host with a controlled fixture in this pass; **inspected** means source or prior evidence only. The actions below are design decisions from this review, not claims that every proposal has shipped.

| Surface | Developer's question; current evidence | Useful peer pattern | Tua direction and decision |
| --- | --- | --- | --- |
| Sprite animation webview | Which frame, duration, origin, or sheet rectangle is wrong? Rendered populated and narrow. The old narrow view put the frame strip below a tall canvas and metadata. | [Aseprite's timeline](https://aseprite.org/docs/timeline/) keeps frames and tags central; its [animation guide](https://www.aseprite.org/docs/animation) exposes per-frame duration and playback. | **Changed:** duration is shown on each frame; the strip follows transport controls; narrow stage is shorter and readouts wrap. Keep the sheet/rectangle inspection. Future: source-linked marker and origin overlays only if compiler metadata gives exact locations. |
| State-machine webview | Which event reaches which state when lines converge? Rendered populated and narrow. Existing routed graph and state inspector are useful, but the machine overview had no complete event list. | [Stately simulation](https://stately.ai/docs/simulate-mode) pairs a diagram with available events and an event log; [Godot's state-machine editor](https://docs.godotengine.org/en/stable/tutorials/animation/animation_tree.html) makes transition properties inspectable. | **Changed:** overview lists every declared event route, selectable by name to highlight the line. Keep the route graph. Never present an event log or simulated reachability until Tua has an explicit simulation contract; the existing runtime overlay is a last sample from one instance. |
| Behavior-tree webview | Which child owns a branch and what is its order? Rendered populated/narrow. Current hierarchy, numbered siblings, collapse, zoom, and source navigation already fit the task. | [Groot2](https://behaviortree.dev/groot/) distinguishes authored tree, live monitor, and log replay. | Keep the tree layout. Add a separate time/status trace only after the inspector can associate node IDs and execution samples reliably. Computed nodes must remain labeled as runtime-resolved. No visual rewrite justified by current fixture. |
| Signal graph webview | Who declares, listens, and emits an event, and with what payload? Rendered populated/narrow; event/file graph and call-site list are already task-specific. | [Godot's Signals dock](https://docs.godotengine.org/en/latest/getting_started/step_by_step/signals.html) reveals the selected signal's receiver and connection. | Favor the event detail and exact source call sites over a large graph. Next qualification: large-game filtering, conflicting payload declarations, and whether a particular listener can be reached. Do not imply static edges describe actual runtime emissions. |
| Module graph webview | Why is a file in the build, or unresolved? Rendered empty/narrow; populated behavior is source-inspected and in prior audit. | [Nx's workspace graph](https://nx.dev/docs/features/explore-graph) can focus a node and identify the file behind a dependency line. | Existing dependency/dependent/export/why tabs are the right structure. Next: use a populated large project to verify click-through from edge to exact `require` and a focused subgraph; keep compiler resolution authoritative. |
| ECS explorer webview | Which systems read or write a component, and which queries include it? Rendered populated/narrow; schema and access rows are source-linked. | [Unity's Entities windows](https://docs.unity.cn/Packages/com.unity.entities%401.0/manual/editor-entities-windows.html) separate components, entities, and systems; the [Systems window](https://docs.unity.cn/Packages/com.unity.entities%401.0/manual/editor-systems-window.html) shows update order and runtime counts. | **Changed:** follow component → system/query → component in the same explorer, with a separate exact-source action. Redundant detail counts were removed so schema and relationships lead. Runtime entity counts and order belong in a clearly live, session-bound inspector. |
| Object-pool explorer webview | Where are items acquired/released, and where might release be missing? Rendered populated/narrow; static call sites and conservative insights are present. | [Unity's Memory Profiler](https://docs.unity.cn/Manual/ProfilerMemory.html) distinguishes allocation measurements from references and snapshots. | Keep call-site list and conservative warnings. Label any ordering as source order, not temporal lifecycle. Use existing development inspector pressure samples for live counts; validate source ↔ live links before a combined pressure view. |
| Audio Workbench webview | Which cue/scene/layer will play and how is it routed? Rendered cue, scene, error, narrow. Source actions, audition, transition test, and authored-versus-analyzed labels already help. | [FMOD's event editor](https://www.fmod.com/docs/2.04/studio/authoring-events.html) organizes assets, routing, transport, timelines, and parameters around an event. | Retain cue/scene split. A future music lane view should show authored layer onset, loop, and quantization on a time ruler only when those values are statically known. Do not invent a live game clock. |
| Procedural-map webview | What shape, route, and sight does a seed produce? Rendered populated/error. A captured form had seed 818 while the old map still reported 817. | [Tiled's map editor](https://doc.mapeditor.org/en/stable/manual/introduction/) foregrounds the map canvas and inspectable tiles. | **Changed:** old map is explicitly marked as the previous sample while generation is pending. Keep the separate isolated-sample disclaimer; do not suggest this is a rendering of the user's map. |
| Assets TreeView and native media | Which asset is this, does it load, and where is it used? Native VS Code image/audio viewers; source-inspected here. | [Godot's FileSystem dock](https://docs.godotengine.org/en/stable/getting_started/introduction/first_look_at_the_editor.html) keeps project resources navigable beside the editor. | Keep native media viewers for ordinary images/audio. Prioritize source/reference navigation, import status, and exact metadata before creating custom replacement webviews. Native viewer behavior needs an installed-project replay. |
| Font webview | Will a UI label or dialogue line fit and look right? Source-inspected and host-tested with a real font asset. Fixed pangram was insufficient for game text. | Aseprite and Godot both expose immediate authoring previews for the active asset; font samples should likewise use a developer's content. | **Changed:** developer can type a game string and see it at four sizes; text survives refresh. It remains browser rendering, with final LÖVE appearance explicitly unverified. |
| Runtime Inspector TreeView | What changed in one running instance? Source-inspected, not a webview. It already offers store history and samples of game systems. | [Redux DevTools](https://redux.js.org/usage/debugging) places action history, state, diff, and trace together. | A store-history diff or event timeline could be valuable, but requires bounded per-session events and production-safe opt-in sampling. Keep the current TreeView until that contract exists; a static store diagram cannot answer this live question. |
| Server Health webview | Is the server doing work, failing analysis, or slow for a sampled method? Rendered empty/narrow; previously six metric cards led with non-actionable zeros. | [Godot's debugger panel](https://docs.godotengine.org/en/stable/tutorials/scripting/debug/debugger_panel.html) groups diagnostic evidence by task. | **Changed:** lead with a snapshot interpretation, compact facts, and slowest sampled p95. Explicitly separate server request timing from visible VS Code menu paint. Do not declare the editor healthy from server timings alone. |
| Generated Lua view | What code will actually run? VS Code text editor, not a webview; source-inspected. | Native code editors already provide selection, search, diff, and line navigation. | Retain native text editor and source-map actions. A custom preview would lose useful editor affordances. Recheck unsaved-source freshness in a full project. |
| LOVE API offline reference | What does this LÖVE symbol mean? Bundled HTML webview, source-inspected. | An API reference works best with search and stable anchors rather than a graph. | Keep reference layout. Qualify command discovery, search, keyboard focus, and link back to current source in an installed host. No source change from this pass. |
| Explain Type / annotations and type reference | Why did this expression become a type or `any`? Native hover/commands, not a dedicated webview; source-inspected. | Compiler provenance is more useful than a decorative type graph. | Keep hover and code navigation primary. Consider a provenance chain only if the semantic resolver can supply stable, precise steps across files. |

## Features without a dedicated preview

These are capability choices, not defects in an existing webview. Build each only after its data contract and target task are explicit.

| Feature | Potential question | Recommended form and prerequisite |
| --- | --- | --- |
| Stores | Which state fields exist, who watches/updates them, and what changed in one run? | Static schema/watcher map beside the existing live inspector history. [Redux DevTools](https://redux.js.org/usage/debugging) is a model for a bounded action/diff list, not proof that Tua currently records one. Need stable store IDs, field/write provenance, and per-session history. |
| Input | Which action maps to each key/button, and are there conflicts? | Searchable binding matrix, not a graph; [Godot Input Map](https://docs.godotengine.org/en/stable/tutorials/inputs/inputevent.html) is a task model. Need static mapping extraction, platform labels, and conflict rules. |
| Tweening | Why does motion jump or ease incorrectly? | Isolated curve/time ruler with exact easing and endpoints; [Godot's animation tracks](https://docs.godotengine.org/en/stable/tutorials/animation/introduction.html) show the value of time-based inspection. Need pure tween evaluation and explicit sample versus in-game motion boundary. |
| Camera | Is the player inside the visible world after scale and shake? | Coordinate/viewport overlay for a selected camera configuration, only with known viewport and transform values. Dynamic follow targets need runtime samples. |
| Shaders | Which uniforms are declared, bound, invalid, or stale? | Uniform/value inspector and compile status tied to source and validator output; avoid a fake shader result without the exact draw context. |
| Vectors and game math | Why is a computed vector wrong? | Native hover/inlay/debug values first. A generic vector playground is less useful than values at the source expression; add one only for an identified reusable task. |

## Sequence and acceptance criteria

1. **Shipped in this pass:** sprite frame timing/narrow hierarchy, state-machine all-route list, bidirectional ECS relationships, server-health snapshot interpretation, custom font text, procedural pending-sample label. Each has host or unit regression coverage and focused docs.
2. **Next relationship qualification:** populated large module/signal/state/ECS graphs against the same compiler output and exact source targets; native asset preview and LOVE reference keyboard path; actual run-session inspector traces. These are evidence gaps, not confirmed defects. Test whether a developer can follow a source path through module → event → system and return without losing context.
3. **Next shared capability:** define stable cross-view relationship IDs and actions (for example, a signal handler's module and a system's component references) in compiler-owned responses. Accept when a link opens the relevant Tua view with the target selected, while source navigation remains a separate action. Avoid guessing relationships from equal names.
4. **Next new preview:** Input binding matrix is the smallest static source-backed candidate. Define a compiler-owned mapping response, conflict semantics, and source ranges first. Accept when a keyboard user can find an action, see every device binding and conflict, and jump to the defining declaration.
5. **Then Stores:** static schema/watcher map only when field/write provenance is stable. A live history/diff panel needs bounded per-session telemetry, pause/disconnect behavior, and explicit development-only instrumentation. Accept when a state change can be traced to its update without claiming a static source graph is a runtime event log.
6. **Later:** tween curve, camera viewport, shader uniforms. Prototype each with one representative fixture and compare the task completion time against source + native editor; drop a preview if it does not shorten the task.
