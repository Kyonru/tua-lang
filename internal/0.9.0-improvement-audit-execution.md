# Prompt: audit and build the Tua 0.9.0 test candidate

Work in `/Users/kyonru/Documents/projects/Experiments/tlua`. Start from the
published 0.8.0 tag. The user is away and authorizes investigation, focused
product and documentation fixes, local atomic unsigned commits, and a final
installable 0.9.0 VSIX. Do not tag, push, publish, or release 0.9.0.

## Objective

Find the highest-value improvements for everyday Tua game development and
implement the feasible, well-evidenced 0.9.0 slices. Cover language correctness,
emitted Lua and runtime behavior, module/type inference, editor responsiveness
and consistency, game-domain APIs, examples, packaging, documentation, and the
trusted test/release gates. Distinguish defects, performance risks, missing
capabilities, design questions, and stale roadmap items.

## Preparation

1. Read `AGENTS.md` if present and the applicable repository skills, especially
   `tua-audit-lead`, language, test, documentation, semantic resolver, LSP,
   LOVE developer experience, architecture, minimal change, and verification.
2. Record the revision, worktree, ignored files, toolchain, available Lua/LÖVE
   and editor hosts, 0.8.0 baseline checks, and previous audit evidence. Protect
   independent work. Use the released VSIX as a comparison where appropriate.
3. Create an inventory from `README.md`, `ROADMAP.md`, focused docs, CLI help,
   config schema, extension contributions, Make targets, and trusted workflows.
   Read the architecture and identify shared semantic and emitted-code paths.

## Investigation and choice

1. Recheck roadmap claims against current code and tests before accepting them
   as open. Select representative bundled projects and small temporary games.
   Exercise check/build/emitted Lua, LSP requests, and installed editor actions
   when available. Measure both protocol latency and visible editor behavior
   without conflating them.
2. Probe high-risk boundaries: imported and inferred class/generic/protocol
   types; unsaved dependency edits; error recovery; LOVE API and asset metadata;
   generated helpers and source maps; stateful game systems; cross-platform
   packaging; cold and contended completion; retained memory. Favor positive,
   negative, and edit-recovery cases where a shared boundary is involved.
3. For each candidate finding, record a minimal reproduction, command/request,
   expected and actual behavior, source location, affected surfaces, existing
   test gap, fix direction, and verification method. Recheck high-impact claims.
   Do not call a documented limit a defect or a skipped test a pass.
4. Rank work by player/developer impact, likelihood, reach, architectural
   leverage, and implementation risk. Choose coherent slices that can be
   verified end to end without a product decision. Implement those; leave
   design-dependent or unqualified work in a prioritized backlog. Avoid a
   cosmetic 0.9.0 made only of version and roadmap edits.

## Implementation

- Preserve a shared source of truth for types, module identities, and lowering.
  Do not patch hover, completion, checker, and signature help separately for one
  semantic cause. Keep dynamic Lua permissive where facts are unavailable.
- Make one independently testable behavior, its meaningful regression coverage,
  and its user-facing documentation/changelog entry per commit. Stage exact
  files and inspect the staged diff. Use `git -c commit.gpgsign=false commit
  --no-gpg-sign`; never add a Codex/AI co-author trailer.
- Mark 0.9.0 in synchronized manifests for the test candidate, keeping
  `CHANGELOG.md` under `[Unreleased]` until an actual release is requested.
  Update the roadmap to remove or clearly mark stale finished items.
- Run focused tests first, then owning crates and cross-surface integration.
  Verify emitted Lua under available Lua/LuaJIT/LÖVE. Compare performance to
  the recorded 0.8.0 workload with matched settings; do not claim a win from
  incomparable measurements.
