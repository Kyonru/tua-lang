Tua developer experience · October 2026

Three engineers build Tetris

A practical evaluation of Tua as a typed Lua and LOVE game-development toolchain. Three simulated engineering personas independently built and ran small falling-block games, then exercised the compiler, linter, formatter, package flow, runtime, language server, documentation, and completion APIs.

Study boundary: these were agent-simulated personas, not recruited human participants. The games and trial notes were intentionally created in temporary directories and were not committed. Findings were accepted only when backed by a minimal reproduction, a real command result, or a direct LSP probe.

Executive verdict

Tua can already carry a real, multi-module LOVE game from source to a runnable .love package. Its strongest surfaces are the build workflow, readable Lua output, LOVE catalog, module navigation, exact input helpers, and actionable type errors. The evaluation also found several cross-module typing and tooling defects that would have become recurring game-project friction. The release-blocking formatter corruption and the highest-confidence compiler/editor defects found by the trials were fixed and regression-tested during this work.

Trial-driven fixes

Fixed · UTF-8-safe formatting

The formatter copied bytes as characters and repeatedly corrupted arrows, accents, CJK, and emoji. It now preserves Unicode scalars and has idempotence coverage for strings, comments, and long-bracket text.

Fixed · LOVE setMode optional flags

love.window.setMode(width, height) is now accepted without inventing an empty flags table. The API override feeds all generated LOVE surfaces and is covered in checker and signature tests.

Fixed · unknown exact module exports

A call such as BoardModule.missingFunction() now reports TL1012 when the module export table is statically known. Unresolved modules, any, dynamic __index proxies, and shadowed locals remain intentionally permissive.

Fixed · named multi-return annotations

A named function annotated with (string, number) now describes two Lua return slots instead of one tuple-valued result. Checker and signature-help tests cover the contract.

Fixed · namespace declaration aliases in arrays

Array literals returned as Types.Point[] from a .d.tua namespace import now resolve their element record before structural checking. The fix also trims normalized type references before project lookup.

Fixed · module constructor contracts

Selected imported return aliases and nested literal unions now survive module export inference and checker-local binding. Hover, completion, and diagnostics consequently agree on the constructor's declared record.

Fixed · indexed literal-union contracts

Indexing an annotated PieceKind[] now retains the imported literal-union item contract in an unannotated local, eliminating the final static workaround in the typed Tetris trial.

Fixed · honest tuple documentation

Native [T, U] syntax is not supported by the current parser. The docs now describe it as LuaCATS interop syntax and use native records or arrays in Tua examples.

Fixed · multiline LSP trial positions

The profiling helper previously added a multiline snippet's total length to its first line. Correct absolute-offset conversion proved that DrawMode completion returns fill and signature help selects parameter 1 after the first comma.

Remaining product gaps

Priority · mutable nilable state narrowing

Natural game state such as Piece | nil remains awkward when a mutable outer/module variable is guarded and then used. The checker is conservative, but the documentation and diagnostic recovery path should explain the boundary; safe same-scope cases deserve a dedicated semantic design.

Priority · LuaCATS imported aliases

Generated annotations can refer to names such as Types.Game without emitting a declaration that downstream Lua tooling can resolve. A declaration companion or stable canonical names are needed before annotation preservation is complete.

Priority · transient project diagnostics

Sequentially opening related files can briefly publish a stale type mismatch before the project revision settles. The final state is correct, but editor adoption should avoid visible red-squiggle flashes.

Policy decision · writes to unknown record fields

game.socre = 10 remains legal on a structurally annotated table under Tua's gradual mutation policy. A high-confidence opt-in lint could catch this without redefining table openness.

Minor · CLI discoverability and generated configuration

tua init --help does not provide contextual subcommand help, and generated diagnostics flags can look contradictory to a newcomer. These are low-risk usability improvements.

Minor · formatter layout

Some multiline signature and condition layouts are stable but visually surprising. This is no longer a correctness issue and should be handled as formatter-style work with golden tests.

Reproducible verification model

Each trial used the same outcome-oriented pipeline. The exact temporary project paths are deliberately not dependencies of this report.

tua fmt --check
tua check --deny-warnings
tua lint --strict
tua build
tua package --name <trial-name>
unzip -t dist/<trial-name>.love
love build-or-package-with-smoke-mode
node lsp-probe.js

Static success alone was not accepted as proof: each game ran under real LOVE, and LSP claims were made through protocol requests. When two LSP results looked wrong, an independent probe compared requested positions to expected offsets and traced both to the test helper rather than the server.

Recommended next game-development work

  1. Design flow-sensitive handling or explicit guidance for mutable optional game state.
  2. Make emitted LuaCATS declarations self-contained across imported Tua aliases.
  3. Add a permanent, repository-owned game-scale fixture that exercises allocation, editor revision adoption, and packaging without committing the exploratory games.
  4. Consider an opt-in unknown-record-field-write lint for teams that want closed-state objects.
  5. Run a small real-human study after the language and extension stabilize; simulated personas are good defect finders, not usability statistics.
